# SecRAGraph 오프라인 포트폴리오 검증 설계

Status: Written-spec review requested
Date: 2026-10-09
Base revision: `ac88e9f`

## 1. 목적과 범위

기존 SecRAGraph의 두 강점인 RAG·LangGraph와 결정적 코드 검사를 면접관이 API 키 없이 직접 확인할 수 있는 증거로 만든다. 사용자는 실제 코드 실행 없이 동일한 데모와 측정값을 재현할 수 있어야 한다. 이번 변경은 공개 GitHub 저장소의 **코드**를 검증 후 갱신하지만, FastAPI 서버를 인터넷에 배포하거나 인증·다중 테넌트를 구현하지 않는다.

이번 릴리스의 두 작업 흐름은 독립적으로 검증한다.

1. 번들 문서를 통한 키 없는 RAG·LangGraph 경로 재현과 출처·경로·한계의 가시화.
2. 라벨이 있는 합성 코드 샘플에 대한 정적 탐지 보강, 기준선·개선 후 성능 측정.

외부 LLM의 추론 품질, 실제 취약점 악용 가능성, 임의 저장소에 대한 탐지율은 이번 측정의 대상이 아니다.

## 2. 기존 상태와 설계 선택

- 지식 그래프는 의도 분류, Qdrant 검색, 제한된 재검색, 근거 답변 또는 답변 보류를 수행한다. 현재 인용 ID의 존재 여부는 확인하지만 `sources`에는 답변에 인용되지 않은 검색 결과도 들어간다.
- 현재 RAG 데모 설명은 제공자 키를 요구하며, 실행 노드·검색 후보·인용과 원문을 한 번에 보여주는 명령 또는 평가 결과가 없다.
- 스캐너는 `PY001`~`PY003`, `SEC001` 네 규칙을 제공한다. Python 위험 호출 규칙은 줄 단위 정규식이라 주석·문자열 오탐과 여러 줄 호출 누락이 가능하다. 라벨 데이터와 정확도 측정은 없다.

검토한 대안은 문서·스크린샷만 보강하는 방법, 로컬 대형 언어 모델을 필수로 설치하는 방법, 키 없는 실제 워크플로 검증을 추가하는 방법이다. 첫 번째는 기능 증거가 약하고 두 번째는 환경 부담과 출력 변동성이 크다. 따라서 세 번째를 채택한다. Qdrant의 메모리 내 로컬 모드, 고정된 경량 임베딩, 결정적 응답 어댑터를 사용하되, 이 결과를 **워크플로·근거 계약 평가**로만 부른다.

## 3. RAG·LangGraph 데모

### 3.1 구성과 흐름

데모 명령은 다음 순서로 동작한다.

1. 저장소가 직접 작성한 `data/knowledge/secragraph-security-guidelines.md`를 기존 Markdown 로더·청커로 읽는다.
2. 별도 서버나 파일 영속화 없이 메모리 내 Qdrant 컬렉션을 만든다. 고정 차원의 결정적 토큰 해시 임베딩으로 문서 조각과 질의를 같은 방식으로 벡터화한다. 이는 로컬 검색 검증용이며 의미 임베딩의 품질을 대변하지 않는다.
3. 기존 `QdrantDocumentRetriever`와 실제 지식 LangGraph를 조립한다. 데모 응답 어댑터는 라벨이 있는 질문을 분류하고 검색된 조각에서 짧은 근거 문장을 골라 실제 조각 ID를 인용한다. 모델을 호출하거나 외부 요청을 보내지 않는다.
4. LangGraph의 노드별 갱신을 수집하되 원시 상태 전체를 직렬화하지 않는다. 허용한 노드 이름, 시도 번호, 검색어의 제한된 표시값, 검색된 조각 ID·제목·섹션·점수, 최종 인용 ID, 답변·경고만 결과에 남긴다.
5. 인용된 번들 문서 조각만 짧은 원문 발췌와 함께 Markdown에 표시한다. 인용 ID와 발췌 원문의 연결을 사용자가 확인할 수 있게 한다.

기본 데모는 로컬 Python 환경만 필요하며 API 키·PostgreSQL·Docker·네트워크가 필요 없다. 기존 실제 제공자 경로와 Compose 경로는 유지하지만, 키가 없어 이번에 실제 LLM 답변 품질을 검증했다고 주장하지 않는다.

### 3.2 평가 데이터와 출력

질문 목록은 기계가 읽는 고정 매니페스트로 관리한다. 최소한 직접 검색 성공, 첫 검색 실패 후 한 번 재작성하여 성공, 최대 재시도 후 근거 부족 답변 보류, 허위 인용 거부를 포함한다. 각 사례는 기대 경로, 관련 섹션, 답변/보류 상태, 인용 조건을 명시한다. 허위 인용은 그래프가 오류로 막는 보안 회귀 사례로 평가하고 정상 답변 사례와 구분한다.

평가 결과에는 사례별 pass/fail과 다음 집계를 담는다: 기대 노드 경로 일치율, 관련 섹션의 retrieval hit@k, 실제 검색 ID에 대한 인용 유효성, 답변 인용과 반환 `sources`의 일치 여부, 근거 부족 시 보류 성공률. 각 분모와 미적용 사례 수를 함께 출력한다. 고정 corpus·매니페스트·임베딩 버전의 식별자와 실행 코드 버전을 기록해 재현성을 확인한다. 시간·UUID 같은 비결정적 값은 합격 판정에 쓰지 않는다.

생성된 JSON/Markdown 증거는 무시되는 `build/evidence/` 아래에 둔다. 명령은 기대 결과가 틀리면 0이 아닌 종료 코드를 반환한다. 문서에는 실제 실행 명령과 결과 발췌를 넣되, 점수를 외부 데이터셋의 성능처럼 제시하지 않는다.

### 3.3 인용 계약 보정

RAG 답변의 `[source:<id>]` 토큰이 현재 검색 결과에 속해야 하는 기존 검증을 유지한다. 공개 응답의 `sources`에는 **실제로 인용된 ID의 출처만** 답변 첫 등장 순서대로 넣는다. 검색되었지만 인용되지 않은 후보는 데모 진단의 `retrieved` 항목에서만 구분해 보여준다. `SourceReference`에 원문 전체를 추가하지 않는다. 일반 설명과 Text2SQL 경로의 출처 계약은 바꾸지 않는다. 근거 문장의 참·거짓은 ID 검증만으로 보증할 수 없음을 문서에 명시한다.

## 4. 결정적 스캐너와 평가

### 4.1 라벨이 있는 안전한 corpus

검사용 corpus는 저장소에서 새로 작성한 합성 텍스트만 사용한다. 사례 매니페스트는 고유 ID, 논리 파일 경로·확장자, 검사할 소스 텍스트, 기대 `(rule_id, line_start)` 집합, 정상 사례 여부를 명시한다. 실제 자격 증명·외부 코드·재배포 권리가 불분명한 소스는 넣지 않는다. 평가 도구는 사례를 임시 디렉터리에 텍스트로만 배치한 뒤 공개 `scan_path` 경로로 검사한다. 대상 파일을 import하거나 실행하지 않으며, 안전한 구문 분석은 허용한다.

기존 네 규칙과 새 규칙마다 실제 탐지 사례 및 주석·문자열·안전한 대안의 대응 정상 사례를 포함한다. 수치 기준선은 이 최종 corpus를 **변경 전 스캐너**에 적용한 값으로 남기고, 개선 후에는 같은 corpus를 다시 실행한다. 새 규칙이 기준선에서 0건인 사실과 기존 규칙의 변화는 분리해서 보여준다. corpus가 구현과 같은 사람이 만든 소규모 합성 집합임을 결과마다 표시한다.

### 4.2 규칙 보강

- Python `PY001`~`PY003`의 호출 판정은 구문 인식 방식으로 바꿔 실행 코드의 호출·인수만 확인한다. 지원 범위는 `eval`, 표준 `subprocess.run/call/Popen`의 리터럴 `shell=True`, `os.system`, `requests` 호출의 리터럴 `verify=False`와 명시적인 단순 import 별칭이다. 주석·문자열은 호출로 보지 않고 여러 줄 호출은 감지한다. 동적 별칭·값 흐름·실행 가능성은 추적하지 않는다.
- 새 Python 규칙은 `yaml.unsafe_load(...)` 및 `yaml.load(..., Loader=yaml.UnsafeLoader)` 같은 명시적인 위험 로더 사용을 탐지한다. `safe_load`와 `SafeLoader`는 제외한다. CWE-502 관련 위험 API 사용 신호이지 입력이 실제 공격자 제어라는 증명은 아니다.
- 새 JavaScript/TypeScript 및 `.env` 규칙은 `NODE_TLS_REJECT_UNAUTHORIZED`를 명시적으로 `0`으로 설정해 TLS 검증을 끄는 경우만 탐지한다. `1`, 문서 문자열, 주석은 제외한다. 일반적인 모든 TLS 설정을 추론하지 않는다.
- 비밀 값 탐지·마스킹 `SEC001`은 유지하되 corpus에서 드러나는 회귀를 수정한다. 새 규칙을 포함한 모든 finding ID, 줄, 증거 마스킹, CWE, SARIF 매핑을 확인한다.

Python 구문 분석이 실패해 호출 규칙의 판정을 신뢰할 수 없으면 해당 파일의 `SEC001` 같은 텍스트 규칙은 계속 실행하고, 호출 규칙의 검사 범위 부족을 보고서 경고에 남긴다. 이를 정상 결과나 진음성으로 세지 않는다. 기존 `scan_text` 사용자는 계속 finding 튜플을 받을 수 있게 호환 경계를 두고, 애플리케이션 스캔 경로가 진단 정보를 함께 수집한다.

### 4.3 측정 계약

매니페스트의 `(case_id, rule_id, line_start)`와 실제 finding을 정확히 비교해 TP·FP·FN을 산출한다. 중복 finding은 한 번만 세고, 잘못된 줄의 탐지는 기대 탐지의 FN이자 별도 FP다. `precision = TP/(TP+FP)`, `recall = TP/(TP+FN)`, `F1 = 2PR/(P+R)`로 계산하고 분모가 0일 때는 `N/A`로 표시한다. 전체·규칙별 값과 정상 사례 중 하나라도 예상 밖 finding이 발생한 비율을 **정상 사례 오경보율**로 보고한다. 이 비율은 임의 코드 전체에 대한 통계적 FPR이 아니다.

모든 사례가 실제로 읽혔는지 확인한다. 지원되지 않는 파일, 시간 초과, 읽기 실패, Python 파싱 실패는 별도 coverage/warning 수치로 드러내며 탐지율 분모에서 조용히 제외하지 않는다. 예상 밖 누락·오탐·경고는 CI 실패다. 별도 단위 테스트는 각 규칙의 양성/음성, 여러 줄·별칭·문법 오류, 비밀 마스킹을 검증한다.

## 5. 저장소 통합과 검증

- 평가 코드는 제품 스캔 엔진·지식 그래프를 호출하는 얇은 모듈/명령으로 둔다. 평가 전용 임베딩과 응답 어댑터는 실제 제공자 구현과 분리해 API 런타임의 기본 설정을 바꾸지 않는다.
- README와 `docs/demo.md`에는 키 없는 두 명령, 측정값의 정확한 범위, 재현 절차, 인용 원문 확인법을 추가한다. 아키텍처·위협 모델에는 평가용 어댑터와 실제 제공자 경계를 명시한다.
- CI는 두 평가 명령을 키·서비스 컨테이너 없이 실행하고 JSON/Markdown 생성과 비정상 종료 조건을 검사한다. Ruff, mypy, pytest, Bandit, 의존성 감사, 기존 CLI/API/E2E/SARIF 테스트는 계속 통과해야 한다.
- 검증이 끝나기 전에는 공개 `main`을 변경하지 않는다. 최종 변경에는 실제 측정 수치, 실행한 명령, 통과/제외 항목을 보고한 뒤 기존 공개 저장소에 안전한 커밋만 반영한다. API 서비스의 인터넷 배포 작업은 하지 않는다.

## 6. 수용 기준

1. 의존성을 설치한 개발 환경에서 실행 시 키·Docker·네트워크 없이 RAG 데모와 스캐너 평가를 수행할 수 있다.
2. RAG 증거에 실제 그래프 경로, 검색 조각, 인용과 번들 문서 발췌, 재시도·보류 사례가 나타난다. 공개 `sources`에는 인용된 출처만 남는다.
3. 스캐너 결과에는 고정 corpus의 변경 전·후 TP/FP/FN, 규칙별 지표, 정상 사례 오경보율, 검사 누락 수가 재현 가능하게 나온다.
4. 새로운 위험 API/설정 규칙과 기존 Python 규칙의 주요 오탐·누락 사례를 테스트하며, 악성 예제는 어느 경로에서도 실행하지 않는다.
5. 두 평가 명령 및 기존 품질·보안·테스트 파이프라인이 통과한다. 문서에는 합성 데이터와 결정적 응답 어댑터의 한계가 눈에 띄게 적힌다.
6. 외부 API 서버는 배포하지 않고, 검증된 코드와 문서만 현재 GitHub 포트폴리오 저장소에 반영한다.
