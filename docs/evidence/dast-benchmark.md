# 일회용 API DAST 벤치마크 — 2026-10-30

## 범위와 재현

`data/evaluation/dast_cases.json`의 작성자 합성 사례 8개를 동일한 일회용 FastAPI에 적용했다. ZAP 패시브 검사 1회와 능동 검사 1회의 **정규화된** 보고서를 정확한 규칙·HTTP 메서드·경로 단위로 채점한다. 각 규칙에는 취약 사례와 정상 대조 사례가 모두 있다. 이 결과는 회귀 관찰값이며 임의의 운영 API에 대한 탐지율 추정치가 아니다.

```text
uv run python -m scripts.run_dast_evidence
```

성공하면 `build/evidence/dast-benchmark.json`·`.md`와 모드별 JSON·Markdown·SARIF가 생성된다. 사례별 방문 또는 공격형 입력 증거가 없거나 검사·격리·정리가 실패하면 **채점하지 않고 실패**한다. 원시 ZAP 보고서, 요청 값, 응답 본문 및 임시 인증 토큰은 보관하지 않는다. CI의 `dast-evidence` 작업도 같은 명령을 실행하고 PR 로그에 집계 수치를 남기며, 신뢰된 `main` 실행의 정규화 결과만 아티팩트로 게시한다.

현재 CI 회귀 기준은 위 manifest SHA-256을 고정하고 `ZAP/10021`·`ZAP/20019`·`ZAP/40018` 각각 **TP 최소 1, FP 0**을 요구한다. 알려진 숫자형 SQLi FN 1건은 보고서에 남긴다. 사례를 바꾸면 새 manifest와 기준 수치를 검토해야 하며, 점수가 기준 아래로 내려가면 CI 로그에 집계를 출력한 뒤 아티팩트를 게시하지 않고 실패한다.

## 측정과 그에 따른 수정

첫 벤치마크 구현 커밋 `6e62012`의 실행에서는 패시브 ZAP이 OpenAPI 시작 경로 밖에 있는 **같은 출처** 경고를 보고해 정규화가 `dast_report_invalid`로 중단됐다. 점수를 낼 수 없으므로 이를 FN이나 TN으로 세지 않았다. `4ea812a`에서 두 모드 모두 같은 출처의 미등록 경로 경고를 정규화 결과에서 제외하도록 수정했다. 다른 출처·형식 오류는 계속 거부한다. 패시브 보고서에도 이 제한을 명시하는 경고를 넣고, 경로 검증·리디렉션 공격 증거 판별을 독립 검토 결과에 맞춰 강화했다. 그 뒤 **같은 manifest**로 8/8 사례를 채점했다.

| 규칙 · 분류 | TP | FP | FN | TN | 정밀도 | 재현율 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `ZAP/10021` 보안 헤더 | 1 | 0 | 0 | 1 | 1.000 (1/1) | 1.000 (1/1) |
| `ZAP/20019` 외부 리디렉션 | 1 | 0 | 0 | 1 | 1.000 (1/1) | 1.000 (1/1) |
| `ZAP/40018` SQL 주입 | 1 | 0 | 1 | 2 | 1.000 (1/1) | 0.500 (1/2) |
| **합계** | **3** | **0** | **1** | **4** | **1.000 (3/3)** | **0.750 (3/4)** |

전체 F1은 **0.857**이다. 패시브 실행 15,360 ms, 능동 실행 19,811 ms, 준비·검사·정리를 포함한 측정 구간은 53,936 ms였다. 개별 규칙 시간은 같은 ZAP 실행을 공유하므로 산출하지 않았다. 평가 대상 외의 정규화된 경고는 15건이고, 탐지된 사례의 CWE 메타데이터 불일치는 0건이다. 15건은 원시 ZAP의 전체 경고 수가 아니다.

남은 FN은 `/sql-numeric-vulnerable`의 숫자형 SQL 주입이다. 테스트 API에서 `1 OR 1=1`은 결과 행을 1개에서 2개로 늘리고 정상 대조 경로는 이를 거부한다. 능동 검사에서 해당 경로로 공격형 입력 65회가 도달했지만 `ZAP/40018` 경고는 없었다. SQLi 규칙의 공격 강도와 경고 임계값을 바꾸는 로컬 실험에서도 이 사례의 탐지가 개선되지 않아 그 설정은 최종 코드에서 제외했다. 이 누락을 다른 규칙의 경고로 대체하거나 점수에서 빼지 않았다.

## 해석 범위

- 취약·정상 라벨은 테스트 API의 HTTP 동작으로 확인했고 ZAP 경고에서 역산하지 않았다. 작성자 사례 8개만으로 실사용 정밀도나 재현율을 주장하지 않는다.
- 능동 검사는 추가 허용 라벨이 있는 일회용 컨테이너의 표시된 GET 시작 경로에서만 시작한다. 시작 경로는 모든 실제 요청의 허용 목록이 아니며, 같은 출처의 미등록 경로 경고는 보고서에 남지 않는다. [ZAP API Scan](https://www.zaproxy.org/docs/docker/api-scan/)은 OpenAPI를 가져와 능동 검사를 실행한다.
- 로컬 Windows 실행에서는 Linux 전용 호스트 게이트웨이 마커 시험을 건너뛰었다. Linux CI의 별도 DAST 작업이 네트워크 격리를 검증한다. 이미지 ID와 시간은 빌드·실행 환경에 따라 달라질 수 있다.
- 추가 규칙·HTTP 메서드·인증 흐름·다양한 운영 API는 이 벤치마크의 분모에 없다. `ZAP/40018`의 탐지 방식은 [ZAP 공식 규칙 설명](https://www.zaproxy.org/docs/desktop/addons/active-scan-rules/)을 참고한다.
