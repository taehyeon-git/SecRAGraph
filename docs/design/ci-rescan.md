# CI 재검사 설계

## 목적과 범위

PR과 `main` push에서만 실행되던 기존 9개 CI·CodeQL 작업을 매주 및 수동 실행에서도 재사용한다. 새 실행은 같은 검사기와 실패 조건을 사용하며, 성공한 신뢰된 `main` 실행의 정규화된 증거만 공개한다. 회원 업로드나 외부 임의 저장소는 이 일정 작업의 대상이 아니다.

## 선택한 방식

- 두 기존 워크플로에 `workflow_dispatch`와 일요일 03:17 UTC의 주간 `schedule`을 추가한다. 별도 복제 워크플로는 검사·정책이 어긋날 위험이 있으므로 만들지 않는다. CI 동시 실행 그룹은 이벤트 종류와 ref를 구분해 새 `main` push가 진행 중인 주간·수동 재검사를 취소하지 않게 한다.
- Git 이력 재검사의 기준점은 [전체 이력 검토 기록](../evidence/git-history-baseline-2026-10-30.md)의 `313a2adc3968a37a1ce63d41a3d7531468a93d00`으로 고정한다. 기존 20개 후보는 숨기지 않고 기록대로 유지하며, 그 뒤의 모든 커밋을 매주 다시 검사한다. 기준점·현재 checkout·이벤트 SHA가 없거나 조상이 아니면 실패한다.
- 이미지 기준선 무변경 검사는 일정·수동 실행에서 현재 `github.sha`의 커밋 blob과 비교한다. PR·push의 기존 비교는 유지한다. Trivy DB는 매 실행 새로 받는다.
- RAG·스캐너 회귀, DAST, 이력, 이미지·SBOM 아티팩트는 `main`의 push·schedule·workflow_dispatch 성공 경로에서만 올린다. 원시 비밀 값과 원시 Trivy JSON은 공개하지 않는다.
- [활성 `main` 규칙](https://github.com/taehyeon-git/SecRAGraph/rules/26191220)이 PR과 9개 필수 작업을 요구한다. 이 규칙은 직접 push를 막지만, PR 작성자가 검사 코드를 수정하는 악의적 변경까지 신뢰하지는 않는다.

## 검증과 한계

이벤트 SHA 선택은 임시 Git 저장소의 진짜 커밋으로 테스트하고, 잘못된 ref·SHA·조상 관계를 거부하는지 확인한다. YAML 테스트는 두 워크플로의 트리거, 기존 작업 이름, 기준선 인자, 게시 조건을 확인한다. 배포 후 `main`에서 수동 실행을 한 번 수행해 모든 작업과 증거 아티팩트를 검증한다. 주간 실행의 실제 범위는 공개 저장소 소스의 CodeQL, 고정 Python 의존성의 OSV, 새로 빌드한 런타임 이미지의 Trivy·SBOM, 일회용 테스트 API의 DAST, 작성자 합성 사례의 회귀 평가다. 회원 업로드나 임의 외부 저장소는 대상이 아니다. GitHub 일정 실행은 지연 또는 비활성화될 수 있어 수동 실행을 보조 경로로 둔다.
