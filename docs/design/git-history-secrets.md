# Trusted Git history secret scanning

## Goal and trust boundary

The existing Gitleaks snapshot scan covers submitted files. This phase adds a separate `security-review scan-history` command for a **trusted local Git checkout** and an independent CI job for this repository. Member uploads, ZIPs, the web UI, and the REST API do not accept a Git path or history-scan request. The scan reads commit data; it never checks out or executes historical code.

The default local command resolves its checkout's HEAD and scans reachable history. Optional `--base` and `--head` select a bounded `(base, head]` range. CI supplies exact commit SHAs for PR and push events without interpolating them into shell strings. For PRs it uses actual `pull_request.head.sha` and `base.sha`, requires exactly one `merge-base --all` result, and fails if the head object is unavailable locally. For pushes it uses event `before` and `after`/`github.sha`; only an all-zero initial `before` selects full history. A force-push/nonancestor or missing SHA fails. Every accepted revision is a full 40- or 64-character hexadecimal object ID, resolved to an existing commit before it reaches Gitleaks. A range requires the base to be an ancestor of the head. Shallow, missing, ambiguous, non-ancestor, empty, or over-limit selections fail closed. The report records the selected bounds and commit count; it does not claim unselected history was inspected.

Preflight uses Git's fixed built-in commands with subprocess argument arrays, no pager, and a sanitized child environment: `GIT_NO_REPLACE_OBJECTS=1`, `GIT_NO_LAZY_FETCH=1`, `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, no external diff/textconv, and empty global/system Git config. The same environment applies to the Gitleaks child. The selection cap is 10,000 commits, the engine deadline is 300 seconds, the metadata report cap is 32 MiB, and the finding cap is 2,000; exceeding any cap fails closed. Before forming log options, each accepted full SHA is canonicalized through `git rev-parse` and verified as a commit. Gitleaks v8.30.1 is pinned and its Git mode receives only fixed `--log-opts` tokens (`--full-history -m --no-ext-diff --no-textconv --no-renames`) and canonical SHAs. `-m` exposes merge-parent diffs that plain `git log -p` otherwise omits; parser identities deduplicate repeats. This matters because that Gitleaks version splits the log-options string on spaces. A root `.gitleaksignore` is rejected so an in-repository ignore file cannot silently hide evidence; explicit `--config` and `--gitleaks-ignore-path` files outside the repository contain the trusted default-rule extension and an empty ignore list, with `--ignore-gitleaks-allow`.

## Secret-free output and provenance

Gitleaks writes a bounded custom JSON template containing only RuleID, File, line/column positions, and Commit. The template uses Sprig `mustToJson` for strings and never references Secret, Match, or Line. `--exit-code 0` lets findings be decided from the parsed report; any nonzero tool exit still means an incomplete/error scan. Standard output and error are not retained or printed. The parser validates the selected commit set, safe relative path (including historical paths no longer present at HEAD), bounded location, and rule identifier before constructing fixed-message `Finding` records with `[secret omitted]` evidence. Tool errors, malformed/missing/oversized reports, timeouts, and incomplete cleanup produce non-success `ScanExecution` status and a nonzero CLI/CI exit.

`Finding.git_commit` is a validated full commit SHA attached only to a source path and line with no unversioned source-to-sink trace. It survives LangGraph enrichment and PostgreSQL round trips. JSON and Markdown show commit provenance. Historical SARIF uses a logical commit/path/line location and commit property, with a commit-sensitive fingerprint; it does not invent a physical location in the current checkout and is not uploaded as a source annotation to GitHub Code Scanning. History execution coverage requires a full head SHA and positive selected-commit count together, allows an optional full base SHA, and is valid only for secret-kind execution; nonhistory executions have no revision fields. Markdown renders this branch before the existing Gitleaks snapshot wording. A nullable database column and check constraint validate historical source location/SHA, preserve old rows, and refuse downgrade while historical rows exist.

## CI evidence and acceptance

A dedicated `git-history-secrets` job checks out full history without persisted GitHub credentials, installs only the SHA-verified pinned Gitleaks binary on a runner with Git, computes the event's exact commit range, and runs the shared history engine once. A validated completed scan first renders and verifies sanitized JSON, Markdown, and historical SARIF from one report; a separate gate step then fails on any finding. This preserves a reviewable main-push artifact even when the finding gate fails, while incomplete or unvalidated output is never uploaded. PRs scan merge-base to actual head, not the synthetic merge commit; pushes scan before to after, with a bounded full-history fallback only for an all-zero initial before SHA. Before relying on incremental pushes, the initial main history is scanned once in full and its bounded result recorded.

Tests create temporary Git repositories with a runtime-generated fake key that is added then deleted, clean/fake credential cases, merge-only additions, root commits, repeated path/line across commits, and malformed refs or reports. Pinned Gitleaks v8.30.1 integration tests prove the fixed log options and `mustToJson` template work. They assert no secret value appears in reports or logs; deleted-at-HEAD findings retain truthful commit identity; unsafe paths, unknown commits, shallow/over-cap history, tool failure, and timeouts cannot yield a clean report. PostgreSQL migration and graph/reporting tests cover provenance preservation.

## Limits

Gitleaks finds pattern-based candidates, not every secret. History coverage is bounded to the selected reachable commits. A detected historical credential still needs revocation and history remediation by its owner; this scanner never rewrites Git history.
