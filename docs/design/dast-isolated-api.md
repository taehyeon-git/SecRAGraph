# Isolated API DAST design

## Goal and boundary

SecRAGraph will scan a **running, disposable test API container** with OWASP ZAP and put the HTTP findings through the same LangGraph evidence and reporting pipeline as source findings. The member upload API will never accept a URL or launch DAST. Source scanning will continue to avoid executing submitted code.

The first DAST mode is ZAP's OpenAPI API scan with `-S`: it imports the API description, sends requests, and performs passive checks. It can identify response-level issues such as missing security headers. It does **not** establish SQL injection, command injection, or other active-probe coverage. An active mode can follow after a separate disposable-target fixture and gate are proven. [ZAP API scan](https://www.zaproxy.org/docs/docker/api-scan/) and [passive scan limits](https://www.zaproxy.org/docs/api/) define this distinction.

## Target authorization and execution

- The local CLI accepts a running Docker container ID/name, internal port, and OpenAPI path. It does not accept an arbitrary URL. The container must explicitly carry `io.secragraph.dast.disposable=true` and be running. CI creates its own labelled fixture.
- The runner creates a random `--internal` Docker network, temporarily connects only the target, starts a **named**, digest-pinned ZAP container on that network, and always force-removes ZAP, disconnects the target, and removes the network in `finally`. ZAP can reach the target alias but has no outside network route.
- Before ZAP starts, a short-lived, named fetcher container on the same internal network reads the target's OpenAPI document with a strict byte cap and timeout. The host reads only that bounded stdout; it never assumes the isolated target is host-reachable. The runner rejects external/remote `$ref`, replaces all `servers` entries with the single target alias, and writes a local schema containing only GET/HEAD/OPTIONS operations. It rejects an empty safe operation set. ZAP imports that local schema; post-result origin checks provide a second guard. The fetcher is force-removed in `finally` too. ZAP `-S` still sends imported requests, so the disposable target label remains mandatory. [ZAP packaged-scan source](https://github.com/zaproxy/zaproxy/blob/main/docker/zap-api-scan.py) confirms this behavior.
- The process has an outer deadline and ZAP's own `-T` deadline. Tool exit codes 0/1/2 mean a completed scan with zero/fail/warn alerts; code 3, timeouts, missing or malformed JSON, and cleanup failures become incomplete/error status, never a clean bill of health. A named ZAP container is removed even when the Docker CLI times out.
- An optional authentication header value is read from a named environment variable and passed with Docker's `-e ZAP_AUTH_HEADER_VALUE` name-only argument and a child environment; the value never appears in argv. `ZAP_AUTH_HEADER_SITE` is fixed to `secragraph-target`. The CLI does not accept or print a token argument. Raw ZAP JSON stays in a temporary directory and is deleted after parsing. The normalized report never stores request/response bodies, full URLs with queries, or header values. [ZAP supplied-auth header support](https://www.zaproxy.org/docs/getting-further/authentication/handling-auth-yourself/) is used only when configured.

## Common result model

`Finding` gains a mutually exclusive HTTP location (`http_method`, `http_path`) alongside its existing source location (`file_path`, `line_start`, `line_end`). An HTTP finding has no source file or line. The existing source JSON fields retain their meaning. HTTP paths are bounded, origin-free, query-free and fragment-free; their method is a bounded HTTP verb. Database columns for source location become nullable and HTTP location columns are added through a migration. Mixed source/HTTP finding ordering and persistence must be deterministic.

The ZAP adapter parses only the official Traditional JSON report's `site[].alerts[].instances[]` fields needed for a finding: numeric plugin ID, risk, confidence, CWE ID, method and URL path. It rejects out-of-scope hosts and malformed reports. Messages/remediation are bounded and sanitized; raw `evidence`, `attack`, `requestHeader`, `responseHeader`, and response fields are deliberately discarded. Stable finding IDs use rule, method and path rather than any secret-bearing content. `ScanExecution` gains `eligible_endpoints` from the sanitized OpenAPI schema and `observed_alert_endpoints` from validated ZAP instances; the latter is **not** an inventory of every request ZAP made. Each report records duration, passive mode and explicit coverage limitations. [ZAP JSON report format](https://www.zaproxy.org/docs/desktop/addons/report-generation/report-traditional-json/) is the source contract.

LangGraph accepts precomputed HTTP findings, warnings and execution coverage, enforces a separate enrichment time budget, enriches verified CWE references when available, and builds a normal `ScanReport`. The graph's rebuilt finding and protected-field checks preserve HTTP location. JSON and Markdown render HTTP locations. SARIF emits logical HTTP locations, never fake repository file paths or code annotations. This DAST SARIF is an artifact, not an upload to GitHub Code Scanning's source-annotation flow. CI parses its JSON and unit tests assert logical HTTP locations; the source-only `scripts/validate_sarif.py` does not apply. Reports disclose that the DAST phase is passive.

## CI and acceptance

CI builds a small disposable FastAPI fixture and calls the same DAST application engine used by the CLI in a separate DAST job. The fixture has a safe public GET route and a protected GET route with a temporary test token. The job requires a completed ZAP run, at least one expected passive alert, proof the protected route received an authenticated request, scoped HTTP locations, a parsable normalized JSON and Markdown report, and teardown. It uploads sanitized reports; it does not publish the raw ZAP output or token. A failing DAST job blocks the CI workflow; making it a GitHub branch-protection **required check** additionally needs a repository ruleset. Unit tests cover invalid labels/ports/paths, off-origin findings, malformed or oversized JSON, secret redaction, status handling, logical SARIF, mixed source/HTTP persistence, LangGraph warnings/execution preservation, and cleanup.

## Remaining phases

The next independent changes are Git-history secret scanning, broad IaC coverage (including Compose), container image package/configuration inspection, and SBOM generation tied to the exact built image. Each gets its own testable phase and CI gate. Existing Opengrep/CodeQL and OSV behavior remains measured separately; none of these changes turns authored regression fixtures into a claim of real-world detection rate.
