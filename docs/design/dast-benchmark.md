# Disposable API DAST benchmark

## Purpose and boundaries

Measure what the pinned ZAP API scan actually detects on labelled vulnerable and benign endpoints, then use the measured gaps to improve the DAST pipeline. This is an **author-written regression corpus**, not an estimate of detection on arbitrary production APIs. No submitted source or arbitrary URL is executed or attacked. The existing full-container-ID, two-label, marked-GET and isolated-network controls remain mandatory.

ZAP's API-Minimal policy includes active SQL injection rule `40018` and external redirect rule `20019`; passive rule `10021` checks the `X-Content-Type-Options` header. A passive off-site redirect warning is not a substitute for `20019`. The API scan is tuned away from XSS, so this corpus does not assign an XSS positive. See [ZAP API scan](https://www.zaproxy.org/docs/docker/api-scan/), [API-Minimal policy](https://github.com/zaproxy/zaproxy/blob/main/docker/policies/API-Minimal.policy), and the [SQL injection](https://www.zaproxy.org/docs/alerts/40018/), [external redirect](https://www.zaproxy.org/docs/alerts/20019/), and [header](https://www.zaproxy.org/docs/alerts/10021/) rule descriptions.

## Corpus and oracle

`data/evaluation/dast_cases.json` is a versioned manifest of eight exact `(mode, rule_id, GET path, expected)` labels: the existing quoted-string SQLi vulnerable/parameterized pair; a numeric SQLi vulnerable/validated pair; an external redirect vulnerable/local-allowlist pair; and a missing/present `nosniff` header pair. Each case has a stable ID, expected CWE and a proof type. The fixture tests establish ground truth from actual HTTP behavior independently of ZAP's alert output. The manifest's raw UTF-8 SHA-256, fixture image ID and source revision identify the evaluated input.

The fixture exposes bounded **counts only** for route requests and attack-shaped inputs; it never returns or logs payloads or temporary credentials. Capture fixture statistics before passive, after passive and after active. Passive cases require their route request count to advance during the passive run. Active cases require an attack-shaped probe count to advance during the active run, including benign controls. Missing counters, missing marked seeds, incomplete ZAP execution, invalid reports or failed cleanup are **unscored failures**, never false negatives or true negatives. Fixture HTTP tests establish each SQL injection, redirect and header label without relying on ZAP alerts.

## Scoring and artifacts

Reuse the same one passive and one active scan that `scripts.run_dast_evidence` already performs. The evaluator rejects duplicate labels, malformed proof keys and missing positive/negative balance, validates both completed reports, verifies exact active seed coverage and per-case proof counts, then scores only the eight assessed `(rule_id, path)` pairs. A matching alert on a vulnerable case is TP; a matching alert on a benign case is FP; a covered vulnerable case without one is FN; and a covered benign case without one is TN. The existing hard-coded SQLi and header *detection* gates move into this scored result, so a measured FN or FP is recorded rather than aborting the run. Completion, isolation and proof gates remain mandatory. Precision, recall and F1 are undefined (`null`) when their denominator is zero. Other **normalized** ZAP rules and paths are counted separately as **unassessed findings**, never folded into FP; active parser filtering means this is not the full raw ZAP alert count. Rule timing is not invented: both rules share a ZAP run, so report only mode execution and total pipeline wall time.

After both scans, the network-isolation check and Compose teardown succeed, publish the existing six normalized reports plus `dast-benchmark.json` and `.md`. The benchmark contains labels, counts, digest/version/coverage/status and timing, but no raw ZAP report, HTTP bodies, request query values or token. The required CI `dast-evidence` job parses both new files and prints summary metrics on pull requests, and uploads the normalized artifacts on trusted `main` only. The benchmark gate fails on incomplete measurement and any explicitly selected regression floor; it does not demand perfect accuracy or hide measured misses. The isolated-network redirect control remains part of the live run.

## Baseline and improvement

Commit the fixture, manifest, evaluator and pipeline first; run the pinned ZAP locally or in Linux CI to record the **baseline** for that immutable manifest. Inspect per-rule TP/FP/FN/TN and failure reasons. Make a narrowly justified scanner or orchestration improvement without changing ground-truth labels, rerun the same manifest, and record both results with hashes and run links in `docs/evidence/dast-benchmark.md`. Keep different denominators or changed fixture semantics separate. Review the final diff and require all protected checks before merging.
